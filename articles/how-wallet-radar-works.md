# How Wallet Radar Works

Wallet Radar is four markdown tables and one script. The tables hold what we could source about software wallets, hardware wallets, crypto cards and ramps. The script turns each row into a 0-100 score. The website reads the same tables and the same scoring code, so what you see is what the script computes.

This page explains where the data comes from, exactly how a score is built, how to read the comparison pages, and where the numbers stop being reliable. Numbers below are from the tables as of 2026-10-16: 33 software wallets, 41 hardware wallets, 51 cards and 22 ramps.

## Where the data comes from

Source order is fixed. We use official docs and sites first, then GitHub, then structured third-party data.

- **Official sites and docs.** Prices, fees, regions, supported chains and product status. Card and ramp rows link to the issuer or provider page.
- **GitHub.** Repository, licence, last commit date and release count come from the GitHub API. Activity uses one rule: last commit within 30 days is Active, 31 to 120 days is Slow, more than 120 days is Inactive.
- **WalletBeat.** For some software wallets we read facts from the MIT-licensed [WalletBeat](https://github.com/walletbeat/walletbeat) data files: account types, licence, audits, bug bounty, funding flags. The snapshot we used is pinned to one commit (2026-10-10) and listed on the Data Sources page.
- **WalletScrutiny.** Used for the reproducible-build attribute on 10 software wallet entries.
- **Issuer pages.** Card network and KYC requirement for cards.

A weekly GitHub Actions job (Mondays, 09:00 UTC) re-reads the GitHub data for every tracked repository and opens a pull request with activity reports. It writes the reports only. It does not edit the comparison tables or any score. A person reads the report and edits the table.

A second weekly job (Mondays, 10:00 UTC) regenerates the Google Merchant Center feed for hardware wallets from a hand-kept price file. It does not feed the scores.

The last recheck was 2026-10-15. Values we re-fetched from a primary page or API that day were updated. Values we could not confirm were marked UNVERIFIED with the reason. Scores were regenerated by script, never typed. The log of what changed, with source URLs, is in `docs/VERIFICATION.md`.

Some data is shown but not scored. Bug bounty status, reproducible build and on-chain verification for software wallets, and card network and KYC for cards, live in a separate file (`data/attributes.json`) with a source URL and a retrieval date on every entry. They appear on detail pages under "Sourced attributes". Where we have no primary source the page says "Not evaluated", which means unknown, not no.

## How a score is computed

Each table row is a line of cells. The scoring code (`frontend/src/lib/scoring.js`) reads those visible cells, turns each one into points with fixed rules, adds the points up and rounds to a whole number between 0 and 100. There are no hidden inputs and no hand adjustments. If you change a cell and run the script, the score changes.

The same code runs in two places. `scripts/sync_table_scores.js` rewrites the Score and Rec cells in the markdown and sorts the rows by score. The site build runs the same functions again and shows the result. A smoke test fails if the markdown and the computed values drift apart.

### What each category scores

| Table | Categories (max points) |
|---|---|
| Software wallets | Core Readiness 20, Release Discipline 15, Developer Safety & Control 24, Ecosystem & Accounts 15, Transparency & Access 14, Maintenance & Assurance 12 |
| Hardware wallets | Security Architecture 34, Transparency & Maintenance 28, Usability & Value 32, Company Track Record 6 |
| Cards | Product Model, Custody & Coverage, Rewards Value, Fee Friction, Delivery Confidence. Points are summed and divided by 90, then scaled to 100 |
| Ramps | Coverage 25, Product Breadth 15, Developer UX 18, Pricing Shape 25, Operational Confidence 15, Company Track Record 2 |

The software score is tuned for one reader: a developer who needs a wallet to test dapps against. That is why Core Readiness is the gate. Full points need a full "Core" cell plus both a mobile app and a browser extension. It is also why fewer releases per month scores higher, and why transaction simulation, custom RPC, testnets, scam alerts and hardware signing are worth 24 points together.

Cards add two rules worth knowing. A card with Status "inactive" loses 28 raw points before scaling. A card with Status "launching" is capped at Situational.

### One wallet, recomputed by the script

Rabby's row in `SOFTWARE_WALLETS.md` reads, in the cells that matter: Core ✅, Rel/Mo ~4, RPC ✅, GitHub linked, Active ✅, Chains one EVM icon, Devices 📱🌐💻, Testnets ✅, License ✅ MIT, API 🌐 Public, Audits ⚠️, Funding 🟢, Tx Sim ✅, Scam ✅, Account EOA+Safe, ENS ⚠️ Import only, HW ✅.

We ran the scoring function on that row from the repo root:

```js
const fs = require('fs');
const { computeSoftwareScore } = require('./frontend/src/lib/scoring.js');
const row = fs.readFileSync('SOFTWARE_WALLETS.md', 'utf8').split('\n').find((l) => l.includes('**Rabby**'));
const cells = row.split('|').slice(1, -1).map((c) => c.trim());
const info = computeSoftwareScore(cells);
console.log(info.score, info.recommendation);
for (const b of info.breakdown) console.log(`${b.label}: ${b.score}/${b.max}`);
```

Output:

```
86 recommended
Core Readiness: 20/20
Release Discipline: 13/15
Developer Safety & Control: 24/24
Ecosystem & Accounts: 7/15
Transparency & Access: 13/14
Maintenance & Assurance: 9/12
```

The 86 matches the Score cell in the table and the breakdown on Rabby's detail page. Here is where each line comes from, read off the code:

| Category | Points | Why |
|---|---|---|
| Core Readiness | 20 | Core is full, and the Devices cell has both mobile and browser |
| Release Discipline | 13 | About 4 releases a month falls in the "3 to 4" tier. 2 or fewer gives 15, 5 to 6 gives 11, more than 8 gives 5 |
| Developer Safety & Control | 24 | Tx simulation 10, custom RPC 4, scam alerts 4, testnets 4, hardware wallet support 2 |
| Ecosystem & Accounts | 7 | One chain family 1, Safe support 3, ENS import only 1, desktop app 2 |
| Transparency & Access | 13 | Public repo 3, open licence 4, public API 3, sustainable funding 3 |
| Maintenance & Assurance | 9 | Active 7, audit cell with ⚠️ scores as an old audit, 2 |

Sum: 20 + 13 + 24 + 7 + 13 + 9 = 86. The weakest line is Ecosystem, 7 of 15, because the table lists one chain family for Rabby. Add a second chain family and the chain line goes from 1 to 3. That is the intended behaviour: the score only moves when the visible data moves.

You can check any table for drift without writing anything:

```
bun scripts/sync_table_scores.js
```

It prints `clean` per table, or `drift` and exits with code 1.

### From score to Rec

The coloured Rec mark (🟢 🟡 🔴 ⚪) is not a fixed cutoff like "70 and up". It is a rank band, set per table each time the script runs:

1. Inactive rows are 🔴 Avoid, whatever their score.
2. For software wallets, a row that fails the developer gate (Core not full, or Developer Safety & Control of 10 or less) is ⚪ Not for dev.
3. The remaining rows are sorted by score. The bottom quarter is 🔴, the next quarter 🟡, the top half 🟢.
4. A "launching" product cannot be 🟢. It is capped at 🟡.

The software table shows how much this matters. Of 33 wallets, 18 are ⚪, because they miss the developer gate. Only 8 are ranked, so the top half is 4 wallets: 4 🟢, 2 🟡 and 2 🔴 from the ranking, plus 7 inactive rows in 🔴 for a total of 9 🔴. Rabby is 🟢 because it is in the top 4 of 8, not because 86 crosses a line. In the other tables the split is wider: 41 hardware wallets give 18 🟢, 9 🟡, 14 🔴; 51 cards give 23, 13, 15; 22 ramps give 11, 6, 5.

## How to read a comparison

Open Explore. Four tabs sit at the top: Software, Hardware, Cards and Ramps, each with its row count. Use the grid or list switch for cards or a table. The list view is the dense one.

![Explore page, Software tab, table view. Each row starts with a round score badge with a small coloured dot, then the wallet name, platforms, chains, feature marks and licence.](/articles/how-wallet-radar-works/software-table.png)

*Software tab in table view. Rows are sorted by score, highest first.*

### The score badge

The number in the circle is the score out of 100. The colour of the circle, the small dot on its corner and the bar under it all show the Rec band, not the score range. Green is Recommended, yellow is Situational, red is Avoid or Not for dev. The bar length is the score. Hover the badge for the score, the band and the banding rule.

Because the colour is a rank band, a high score can still be red. Safe scores 77 and shows red, because its Core cell is ❌ and the software table marks it Not for dev. The same score can also be green in one table and yellow in another.

### Columns and marks

Column headers have a help icon with the definition for that column. Feature columns use three marks: a green tick for full support, a yellow tilde for partial, a dash for none. Hover a mark for its label.

| Mark | Meaning |
|---|---|
| `~` before a number | Approximate or volatile value, such as a price or a release rate |
| `UNVERIFIED` | We could not confirm the value from a primary source on the check date. The old value is kept and the reason is written next to it |
| `‡` in the hardware and ramps tables | Same as UNVERIFIED. A footnote under the table says why. Cells marked this way still feed the score |
| `‡` and other symbols in the software table | Row notes (†, §, ‡, ⁂, ∆) explained in the note under that table. They are not verification marks |
| `TBD` | No sourced value yet. The scoring code gives a low default, so the score is a lower bound |
| Status Inactive, or "Discontinued" in the text | The product has shut down, been wound down or paused. It stays in the table so people can see it, and the score is penalised |

### Filters, sort and search

The search box matches names. Sort options depend on the tab: software sorts by score, name, chain count or release frequency; hardware by score, name or price; cards by score, name or maximum cashback; ramps by score or name. The Filters button opens the panel.

![The Software tab with the Filters panel open: a score range slider and drop-downs for Recommendation, Activity Status, Platforms, License, Features, Account Types and Funding, under the search box and sort menu.](/articles/how-wallet-radar-works/filters-sort.png)

*Filters and sort on the Software tab.*

Software filters cover Rec, platform, licence, features, account type, activity and funding, plus a score range. Hardware adds price range, open-source level and connectivity. Cards add type, custody, status, region and minimum cashback. The quick presets above the table (for example Core Wallets, Open Source, Air-Gapped, No Annual Fee) set several filters at once.

### Compare

Press the plus button on up to four rows, then open Compare. The compare view puts the rows side by side: score, Rec, each feature, release rate, and the category scores. It marks the best and worst value on a row. You can export a CSV or copy a link to the exact comparison.

![Lower half of the compare view for Rabby and MetaMask: Tx simulation, scam alerts, custom RPC, account types, releases per month with best and worst marked, and the start of the category score breakdown.](/articles/how-wallet-radar-works/compare-view.png)

*Rabby (86) and MetaMask (80), side by side. The top of the view shows both scores and the Rec.*

### State lives in the URL

Everything above is stored in the address, so a link reproduces your view. The main keys are:

| Key | Meaning |
|---|---|
| `tab` | `software`, `hardware`, `cards` or `ramps` |
| `view` | `table` (omitted for the default grid) |
| `sw`, `hw`, `cd`, `rp` | Selected rows per tab, comma-separated, at most four |
| `compare=1` | Open the compare view |
| `search` | Search text |
| `sSort`, `hSort`, `cSort`, `rSort` | Sort as `field:direction`, for example `chains:desc` |
| `sFilters`, `hFilters`, `cFilters`, `rFilters` | Filters as JSON |

For example, `/explore/?tab=software&view=table&sw=rabby,metamask&compare=1` opens the compare view above. Unknown values are dropped, so a stale link falls back to the default instead of breaking.

### Detail pages

Each row has a page, such as `/wallets/software/rabby/`. It shows the score, the category table (weight, points earned, completion), the sourced attributes with source links, and the closest rows by score.

![Rabby's detail page in dark mode: score 86/100, the category breakdown bar and the points table.](/articles/how-wallet-radar-works/wallet-detail.png)

*A detail page. The points match the script output above.*

### Cards and discontinued products

Card rows keep products that have shut down. Cypher Card is marked Discontinued and scores 1. Ready Card is marked Discontinued and scores 41. Their Status is Inactive, and that is what drives the penalty and the red band. To list them, set the Status filter to Inactive. The table then shows 4 of the 51 cards.

![The Cards tab filtered to Status Inactive: Cypher Card (1), Spendly (29) and Ready Card (41), each with a red badge and an Inactive status.](/articles/how-wallet-radar-works/cards-discontinued.png)

*Cards filtered to Status Inactive. The raw text of the source cell is shown under each name, including the Discontinued note.*

The category table on a card's detail page does not show the penalty. Cypher Card's five categories add up to 29 raw points. The 28-point inactive penalty is taken off after that, then the result is scaled, which gives 1.

On a phone the table keeps all its columns and scrolls sideways. The score badge and the name stay in the first screen.

## Limits

- **A score ranks rows inside one table.** An 86 software wallet and an 86 ramp are not comparable. Hardware, cards and ramps use different categories and different weights.
- **The software score is built for developers.** It rewards mobile plus browser coverage, simulation, RPC control and slow release cadence. If you hold a long-term balance and never test dapps, the ranking may not match what you want. The weights are in one file, so you can read them and disagree.
- **Rec is relative.** The software ranking is over 8 wallets, so one new row can move a wallet from 🟢 to 🟡 with no change to its own data.
- **Only table cells count.** Anything that is not a column, such as support quality, incident history or a team's reputation, is outside the score. Hardware incidents appear in the details pages, not in the number.
- **Unsourced cells still score.** TBD gets a low default. UNVERIFIED and ‡ cells keep their old value and still feed the score.
- **Not every cell was re-fetched.** Audit dates, funding and chain lists for software wallets are the least rechecked fields. The verification log (`docs/VERIFICATION.md`) lists what is still UNVERIFIED.
- **Some pages block automated checks.** Several issuer and store sites return 403 or a browser check. Those values stay UNVERIFIED until someone confirms them by hand.
- **Rates and prices move.** Fees, cashback, regions and prices change without notice. Treat the table as a starting point and read the provider page before you sign up or pay.
- **QR payment providers are not scored by the script.** Their scores are older estimates and are not recomputed.
- **GitHub activity is a proxy.** A wallet can ship from a private repo or from a different repo than the one we track. Private-repo wallets show as Private, with a lower activity score.

## Check it yourself

Everything here is in the public repo: the tables at the root, the scoring in `frontend/src/lib/scoring.js`, the sync in `scripts/sync_table_scores.js`, the data sources page and the contributing guide. If a number is wrong, a pull request that changes the cell and the source link is the fastest fix. Run the sync script, and the score follows.
